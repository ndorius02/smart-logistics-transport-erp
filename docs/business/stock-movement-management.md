# Stock Movement Management — Business Rules

## 1. Purpose

The **Stock Movement Management** module records and controls all physical stock changes within the ERP.

Inventory represents the **current stock state**.

Stock Movement represents the **transaction and history explaining how that stock changed**.

The module provides traceability for stock increases and decreases.

Example:

```text
Inventory before movement:
quantity = 100.000

Stock Movement:
STOCK_IN +25.000

Inventory after movement:
quantity = 125.000
```

Stock quantities must not normally be modified directly.

Operational stock changes must be performed through Stock Movement operations.

---

## 2. Stock Movement Definition

A StockMovement contains:

- Technical identifier
- Business reference
- Product
- Warehouse
- Movement type
- Quantity
- Reason
- Notes
- Movement timestamp
- User who created the movement
- Creation timestamp

Example:

```text
Reference:       SM-2026-000001
Product:         PRD-ELEC-001
Warehouse:       WH-BRU-001
Type:            STOCK_IN
Quantity:        25.000
Reason:          Supplier receipt
Created By:      admin@example.com
```

---

## 3. Relationship with Inventory

A Stock Movement operates on exactly one Inventory position.

Conceptually:

```text
Product
   |
   |
Inventory
   |
   +------ Warehouse
   |
   |
   *
StockMovement
```

The Inventory position is identified by:

```text
product_id + warehouse_id
```

The Stock Movement updates the corresponding Inventory quantity.

---

## 4. Movement Types

The following movement types are supported in V1:

```text
STOCK_IN
STOCK_OUT
ADJUSTMENT_IN
ADJUSTMENT_OUT
```

### STOCK_IN

Represents a normal physical stock receipt.

Examples:

- supplier delivery;
- goods receiving;
- returned goods entering stock.

Effect:

```text
inventory.quantity =
    inventory.quantity + movement.quantity
```

### STOCK_OUT

Represents a normal physical stock issue.

Examples:

- outbound shipment;
- customer delivery preparation;
- goods leaving the warehouse.

Effect:

```text
inventory.quantity =
    inventory.quantity - movement.quantity
```

### ADJUSTMENT_IN

Represents a positive inventory correction.

Examples:

- physical count found more stock than expected;
- correction of a previous stock error.

Effect:

```text
inventory.quantity =
    inventory.quantity + movement.quantity
```

### ADJUSTMENT_OUT

Represents a negative inventory correction.

Examples:

- damaged goods;
- missing stock;
- inventory count correction;
- expired goods.

Effect:

```text
inventory.quantity =
    inventory.quantity - movement.quantity
```

## 5. Business Rules

### BR-SM-001 — Movement Identifier

Every Stock Movement must have a unique technical identifier.

The identifier is generated by the application.

API clients must not provide or modify it.

---

### BR-SM-002 — Movement Reference

Every Stock Movement must have a unique business reference.

Example:

```text
SM-2026-000001
```

The reference must:

- be mandatory;
- be unique;
- be normalized to uppercase.

---

### BR-SM-003 — Product Is Required

Every Stock Movement must reference one Product.

The Product must exist.

---

### BR-SM-004 — Product Must Be Active

New Stock Movements may only be created for active Products.

Historical movements remain readable if a Product is later deactivated.

---

### BR-SM-005 — Warehouse Is Required

Every Stock Movement must reference one Warehouse.

The Warehouse must exist.

---

### BR-SM-006 — Warehouse Must Be Active

New Stock Movements may only be created for active Warehouses.

Historical movements remain readable if a Warehouse is later deactivated.

---

### BR-SM-007 — Inventory Position Must Exist

A Stock Movement may only be performed if the corresponding Inventory position exists.

The backend must find:

```text
product_id + warehouse_id
```

in Inventory.

If no Inventory position exists, the movement must be rejected.

Stock Movement must not silently create Inventory records.

---

### BR-SM-008 — Movement Type Is Required

Every movement must use one of the supported movement types:

```text
STOCK_IN
STOCK_OUT
ADJUSTMENT_IN
ADJUSTMENT_OUT
```

---

### BR-SM-009 — Movement Quantity Must Be Positive

The movement quantity is always expressed as a positive value.

Example:

```text
25.500
```

is valid.

```text
0
```

is invalid.

```text
-25
```

is invalid.

The movement type determines whether the quantity increases or decreases Inventory.

Therefore clients must never send negative quantities.

---

### BR-SM-010 — Decimal Quantities

Stock Movement quantities support decimal values.

Database precision:

```text
NUMERIC(15,3)
```

This supports units such as:

```text
PIECE
BOX
PALLET
KILOGRAM
LITER
METER
```

Example:

```text
150.750 KILOGRAM
32.500 METER
5.000 PALLET
```

---

### BR-SM-011 — Stock Must Never Become Negative

A decreasing movement must never produce negative physical stock.

For:

```text
STOCK_OUT
ADJUSTMENT_OUT
```

the following condition must hold:

```text
currentQuantity >= movementQuantity
```

Example:

```text
Current stock: 10.000
Movement: STOCK_OUT 15.000
```

must be rejected.

---

### BR-SM-012 — Reserved Quantity Must Remain Valid

A stock decrease must not cause:

```text
reservedQuantity > quantity
```

after the movement.

Example:

```text
quantity = 100
reservedQuantity = 40

STOCK_OUT = 70
```

would result in:

```text
quantity = 30
reservedQuantity = 40
```

which is invalid.

Therefore the operation must be rejected.

---

### BR-SM-013 — Movement Is Immutable

Once a Stock Movement has been successfully created, it must not be modified.

There is no normal:

```http
PUT /api/stock-movements/{id}
```

endpoint.

If an operational mistake occurs, a compensating movement must be created.

Example:

```text
Incorrect:
STOCK_IN +50

Correction:
ADJUSTMENT_OUT 10
```

This preserves audit history.

---

### BR-SM-014 — Movement Must Not Be Deleted

Stock Movements must not be physically deleted through the API.

There is no:

```http
DELETE /api/stock-movements/{id}
```

endpoint.

Historical stock traceability must be preserved.

---

### BR-SM-015 — Atomic Transaction

Creating a Stock Movement and updating Inventory must occur in the same database transaction.

The operation must behave atomically:

```text
Create movement
+
Update inventory
=
one transaction
```

If either operation fails, neither change may be committed.

---

### BR-SM-016 — Reason

A movement may contain a business reason.

For adjustment movements, reason should be mandatory.

Examples:

```text
Physical inventory correction
Damaged goods
Expired goods
Receiving discrepancy
```

---

### BR-SM-017 — Notes

Optional notes may provide additional operational information.

Maximum length:

```text
500 characters
```

---

### BR-SM-018 — Movement Date

Each Stock Movement must record the timestamp when the business operation occurred.

For V1, the backend assigns the movement timestamp when the movement is created.

---

### BR-SM-019 — Created By

Every movement must record which authenticated user created it.

This provides operational traceability.

Example:

```text
createdBy = admin@example.com
```

The client must not provide this value directly.

It must come from the authenticated Spring Security context.

---

## 6. Inventory Update Rules

### Increasing movements

The following types increase Inventory:

```text
STOCK_IN
ADJUSTMENT_IN
```

Calculation:

```text
newQuantity =
    currentQuantity + movementQuantity
```

### Decreasing movements

The following types decrease Inventory:

```text
STOCK_OUT
ADJUSTMENT_OUT
```

Calculation:

```text
newQuantity =
    currentQuantity - movementQuantity
```

Before decreasing stock, the backend must verify:

```text
newQuantity >= 0
```

and:

```text
reservedQuantity <= newQuantity
```

---

## 7. Movement History

Users must be able to retrieve movement history:

- all movements;
- movements by Product;
- movements by Warehouse;
- movements by Inventory position;
- movements by movement type.

All history endpoints must support pagination.

| Operation | ADMIN | MANAGER | WAREHOUSE_OFFICER | TRANSPORT_COORDINATOR |
|---|:---:|:---:|:---:|:---:|
| View movements | ✅ | ✅ | ✅ | ✅ |
| Search movement history | ✅ | ✅ | ✅ | ✅ |
| STOCK_IN | ✅ | ✅ | ✅ | ❌ |
| STOCK_OUT | ✅ | ✅ | ✅ | ❌ |
| ADJUSTMENT_IN | ✅ | ✅ | ✅ | ❌ |
| ADJUSTMENT_OUT | ✅ | ✅ | ✅ | ❌ |

## 11. Database Constraints

The database must protect essential movement data.

Required constraints:

```text
PRIMARY KEY (id)
```

```text
UNIQUE(reference)
```

```text
FOREIGN KEY (product_id)
REFERENCES products(id)
```

```text
FOREIGN KEY (warehouse_id)
REFERENCES warehouse(id)
```

```text
CHECK(quantity > 0)
```

---

## 12. Stock Movement vs Inventory

The responsibilities are deliberately separated.

### Inventory

Represents:

```text
CURRENT STOCK STATE
```

Example:

```text
quantity = 125.500
reservedQuantity = 20.000
availableQuantity = 105.500
```

### Stock Movement

Represents:

```text
HOW THE STOCK CHANGED
```

Example:

```text
STOCK_IN +25.500
```

Therefore:

```text
Inventory
→ current state

StockMovement
→ transactional audit history
```

---

## 13. Warehouse Transfers

Warehouse transfers are not directly implemented as a single movement type in V1.

A future warehouse transfer will conceptually involve:

```text
Warehouse A
STOCK_OUT
    |
    v
TRANSFER
    |
    v
Warehouse B
STOCK_IN
```

A dedicated Transfer operation may later coordinate both movements atomically.

---

## 15. Summary

Stock Movement Management provides the transactional history behind Inventory.

Its responsibilities are:

- recording every physical stock change;
- updating Inventory atomically;
- preventing negative stock;
- preserving reserved-stock consistency;
- recording the authenticated user responsible for the operation;
- maintaining immutable movement history;
- providing Product and Warehouse movement traceability.

Inventory answers:

```text
How much stock exists now?
```

Stock Movement answers:

```text
Why and how did that stock change?
```
