# Product Category Management — Business Rules

## 1. Purpose

The **Product Category Management** module maintains the reference categories used to classify products in the ERP.

A product category is considered **master data**.

It provides a controlled and reusable classification system for Product Management and future modules such as:

- Inventory Management
- Procurement
- Purchase Orders
- Cargo Management
- Shipment Management
- Reporting

Product categories are managed independently from products.

---

## 2. Product Category Definition

A product category contains:

- Technical identifier
- Category code
- Category name
- Description
- Active status
- Creation timestamp
- Last update timestamp

Example:

```text
Code:        ELEC
Name:        Electronics
Description: Electronic equipment and accessories
Active:      true
```

---

## 3. Business Rules

### BR-PCAT-001 — Category Identifier

Each product category must have a unique technical identifier.

The identifier is generated by the application.

API clients must not provide or modify it.

---

### BR-PCAT-002 — Category Code

Each category must have a business code.

The code:

- is mandatory;
- must be unique;
- must not be blank;
- must not be reused by another category.

Examples:

```text
ELEC
FOOD
AUTO
IND
PHARMA
```

---

### BR-PCAT-003 — Category Code Normalization

Before persistence, the category code must be:

- trimmed;
- converted to uppercase.

Example:

```text
" elec "
```

becomes:

```text
ELEC
```

This ensures consistent category codes across the ERP.

---

### BR-PCAT-004 — Category Name

Each category must have a name.

The category name:

- is mandatory;
- must not be blank;
- represents the business-readable category designation.

Examples:

```text
Electronics
Food & Beverage
Automotive
Industrial Equipment
Pharmaceutical
```

---

### BR-PCAT-005 — Category Name Uniqueness

Category names must be unique regardless of letter case.

For example:

```text
Electronics
electronics
ELECTRONICS
```

must be considered the same category name.

This prevents duplicate categories caused only by capitalization differences.

---

### BR-PCAT-006 — Description

A category may have an optional description.

The description provides additional business information about the category.

Maximum length:

```text
500 characters
```

---

### BR-PCAT-007 — Default Active Status

A newly created category must be active by default.

```text
active = true
```

The API client must not control the initial active status during category creation.

---

### BR-PCAT-008 — Category Deactivation

Product categories must not be physically deleted through normal business operations.

A category may instead be deactivated.

Deactivation preserves:

- historical product references;
- inventory history;
- future transactional references;
- audit information.

---

### BR-PCAT-009 — Category Reactivation

An inactive category may be reactivated by an authorized user.

Reactivation must preserve:

- category ID;
- category code;
- existing product relationships;
- audit history.

Reactivation does not create a new category.

---

### BR-PCAT-010 — Inactive Category Usage

An inactive category remains readable for historical purposes.

However, an inactive category must not be assigned to a new product.

Existing products already referencing the category remain valid.

This ensures historical consistency while preventing new operational usage of inactive reference data.

---

### BR-PCAT-011 — Category Update

Authorized users may update:

- code;
- name;
- description.

The following fields are managed by the application and must not be modified directly by API clients:

- technical identifier;
- creation timestamp;
- last update timestamp.

Uniqueness rules must continue to be enforced during updates.

---

### BR-PCAT-012 — Update Must Preserve Uniqueness

When updating a category:

- the category may retain its own existing code;
- the category may retain its own existing name;
- another category's code cannot be reused;
- another category's name cannot be reused.

Uniqueness checks must exclude the category currently being updated.

---

### BR-PCAT-013 — Product Relationship

Each Product must belong to one ProductCategory.

The relationship is:

```text
ProductCategory
      1
      |
      |
      *
   Product
```

A product category may contain many products.

A product belongs to exactly one category.

The database relationship will therefore be implemented as:

```text
ProductCategory 1 ---- * Product
```

with the foreign key stored on the Product side.

---

### BR-PCAT-014 — Category Deactivation Does Not Cascade

Deactivating a category must not:

- delete products;
- automatically deactivate products;
- delete inventory records;
- remove product history;
- remove existing transactional references.

ProductCategory and Product have independent lifecycles.

---

### BR-PCAT-015 — Audit Information

The application must maintain:

```text
createdAt
updatedAt
```

`createdAt` is assigned when the category is created.

`updatedAt` is updated whenever the category is modified.

These fields are managed by the existing `Auditable` base entity.

API clients must not provide or modify these values.

---

## 4. Search Rules

Users must be able to search categories by:

- category code;
- category name.

Search operations must:

- be case-insensitive;
- support partial matching;
- support pagination.

Example:

```text
Search: "elect"
```

may return:

```text
Electronics
Electrical Equipment
```

Search operations must not modify category data.

---

## 5. Pagination

Category list and search operations must support pagination.

Supported pagination parameters:

```text
page
size
sort
```

Example:

```http
GET /api/product-categories?page=0&size=10&sort=name,asc
```

The default sorting strategy should use the category name in ascending order.

---

## 6. Product Category Lifecycle

A product category follows this lifecycle:

```text
       CREATE
         |
         v
       ACTIVE
         |
         | deactivate
         v
      INACTIVE
         |
         | activate
         v
       ACTIVE
```

There is no physical delete operation in V1.

| Search categories | ✅ | ✅ | ✅ | ✅ |
| View category details | ✅ | ✅ | ✅ | ✅ |
| Create category | ✅ | ✅ | ❌ | ❌ |
| Update category | ✅ | ✅ | ❌ | ❌ |
| Activate category | ✅ | ✅ | ❌ | ❌ |
| Deactivate category | ✅ | ✅ | ❌ | ❌ |

The following roles may view and search product categories:

```text
ADMIN
MANAGER
WAREHOUSE_OFFICER
TRANSPORT_COORDINATOR
```

### Management Access

The following roles may create, update, activate and deactivate product categories:

```text
ADMIN
```

## 9. Planned REST API

### Create Category

```http
POST /api/product-categories
```

Example request:

```json
{
  "code": "ELEC",
  "name": "Electronics",
  "description": "Electronic equipment and accessories"
}
```

The backend automatically assigns:

```text
id
active = true
createdAt
```

---

### Get Categories

```http
GET /api/product-categories
```

Example:

```http
GET /api/product-categories?page=0&size=10&sort=name,asc
```

---

### Get Category by ID

```http
GET /api/product-categories/{id}
```

---

### Search by Code

```http
GET /api/product-categories/search/code?code=ELEC
```

The search must be case-insensitive.

---

### Search by Name

```http
GET /api/product-categories/search/name?name=elect
```

Partial and case-insensitive matching must be supported.

---

### Update Category

```http
PUT /api/product-categories/{id}
```

Example request:

```json
{
  "code": "ELEC",
  "name": "Electronics",
  "description": "Electronic equipment, devices and accessories",
  "active": true
}
```

---

### Activate Category

```http
PATCH /api/product-categories/{id}/activate
```

---

### Deactivate Category

```http
PATCH /api/product-categories/{id}/deactivate
```

## 11. Product Category vs Unit of Measure

ProductCategory must be managed as an entity because categories represent configurable business reference data.

Categories may evolve according to business requirements.

For example:

```text
Electronics
Food & Beverage
Automotive
Industrial Equipment
Pharmaceutical
Packaging
Chemicals
```

The business may add new categories without requiring an application deployment.

Therefore:

```text
ProductCategory → Entity / database reference data
```

By contrast, UnitOfMeasure represents a smaller and more stable controlled set of technical values.

For V1:

```text
PIECE
BOX
PALLET
KILOGRAM
LITER
METER
```

Therefore:

```text
UnitOfMeasure → Java Enum
```

## 12. Relationship with Product Management

ProductCategory is reference master data.

Product is product master data.

The relationship will be:

```text
ProductCategory
      |
      | 1
      |
      | *
   Product
```

Example:

```text
ProductCategory
────────────────────────
ELEC
Electronics
        |
        |
        +── Dell Latitude 5550
        |
        +── Lenovo ThinkPad
        |
        +── Samsung Monitor
```

A Product will reference its category using a foreign key.

Conceptually:

```text
products.category_id
        |
        v
product_categories.id
```

---

## 13. Relationship with Inventory Management

ProductCategory does not directly manage inventory quantities.

The future relationship will be:

```text
ProductCategory
      |
      | 1
      |
      | *
   Product
      |
      | 1
      |
      | *
  Inventory
      *
      |
      | 1
      |
  Warehouse
```

Responsibilities remain separated:

```text
ProductCategory
→ product classification

Product
→ product master data

Inventory
→ stock state per product and warehouse

StockMovement
→ history of stock changes
```

## 16. Summary

ProductCategory is a **reference master-data entity** used to classify products consistently across the ERP.

Its responsibilities are:

- providing controlled product classification;
- maintaining unique category codes;
- maintaining unique category names;
- supporting category activation and deactivation;
- preventing inactive categories from being assigned to new products;
- preserving historical product relationships;
- providing reusable reference data for Product Management;
- supporting future Inventory, Procurement, Cargo, Shipment and Reporting modules.

ProductCategory does not manage product stock or inventory quantities.

Those responsibilities belong to the Inventory Management domain.
